## Environment

Disposable Tart clones of `ghcr.io/cirruslabs/macos-tahoe-base`, macOS 26.6.2, `csrutil status`
enabled, Gatekeeper assessments enabled. The helper runs as a system LaunchDaemon
(`KeepAlive`, `AbandonProcessGroup`) and supervises the driver daemon unless another one runs.
Input comes from a scripted virtual source keyboard (`fixture-keyboard`); a foreground AppKit
window (`Sink.app`) and an optional consuming HID event tap record what reaches applications.
Every fixture refuses to run unless `hw.model` begins with `VirtualMac`. Guest-only VNC input
answered macOS consent UI.

Reproduce with a VM that has the driver approved:

```sh
AZAD_CODESIGN_IDENTITY='Developer ID Application: …' \
  python3 crates/azad-capture/tests/vm/run_matrix.py --vm <tart-vm> --out <dir> --stage
python3 crates/azad-capture/tests/vm/run_matrix.py --vm <tart-vm> --out <dir> --permission revoke
python3 crates/azad-capture/tests/vm/run_matrix.py --vm <tart-vm> --out <dir> --only negative_no_permission
python3 crates/azad-capture/tests/vm/run_matrix.py --vm <tart-vm> --out <dir> --permission request
#   (answer the prompt: Open System Settings, enable Azad Capture)
python3 crates/azad-capture/tests/vm/run_matrix.py --vm <tart-vm> --out <dir> --permission wait-granted
```

## Sequence and pass criteria

Each capturing scenario plays 28 reports: Option+Space pressed and released, pressed again, Up
during the held Space, Option released before Space, then Return, Escape, all four arrows,
keypad Enter, Shift+Return and `a`. The client publishes an overlay context with listen modifier
Option and every overlay key enabled.

A scenario passes only if all of these hold:

- exactly the 12 expected actions arrive in order, with monotonic capture timestamps;
- no claimed key (Space, arrows, Escape, keypad Enter, unshifted Return) reaches the foreground
  window or the competing tap;
- Shift+Return (with Shift) and `a` each arrive exactly once down and once up, across the window
  and any consuming tap, and `a` carries no stuck Option;
- the helper reports a seized device.

### Permission lifecycle

With the grant revoked (`tccutil reset ListenEvent ai.azad.capture`) the helper reports
`permission_denied` with no devices and never a healthy status. A root daemon cannot be prompted
(`tccd`: "Service kTCCServiceListenEvent does not allow prompting"), so onboarding runs the same
bundle from the user's session with `--request-access`. macOS shows its standard "Azad Capture
would like to receive keystrokes" prompt ([screenshot](evidence/2026-09-29-access/permission/consent-prompt.png));
Open System Settings lists Azad Capture switched off ([screenshot](evidence/2026-09-29-access/permission/listed-off.png)),
and one switch grants it ([screenshot](evidence/2026-09-29-access/permission/granted.png)). IOKit
caches a denial for the life of a process, so the helper probes with a fresh child process and
re-executes itself on a grant; the recorded run shows `permission_granted_restart`, then
`permission: granted`, and the following `baseline` passed without a manual restart. The grant
is recorded against the bundle identifier (`client_type` 0) and designated requirement; during
development one grant stayed effective across three rebuilt, re-signed helper versions with code
changes (their hashes were not recorded, so this is an observation, not part of the evidence set).

### Coexistence with Karabiner-Elements

With Karabiner-Elements set up (background services, Accessibility, keyboard type ANSI):

- Karabiner grabbed the VM's USB keyboard and only observed the Karabiner-driver keyboards,
  including Azad's output (`hid device events monitor is started (observed)`), so there is no
  loop.
- Karabiner's daemon rebinds the shared driver socket; the helper stops the daemon it started
  and attaches to Karabiner's. One daemon ran during the scenario.
- The helper yielded the physical keyboard to Karabiner (`yielded`) and seized Karabiner's output
  keyboard (vendor 0x05ac, Karabiner product strings).

Nothing produces input on the VM's USB keyboard, so this run proves the arrangement, not key flow
through Karabiner. `cooperative_remapper` proves key flow through an owner of the same shape.

## Findings that shaped the helper

- macOS delivers keys from an unidentified keyboard to event taps but not to applications, and
  opens Keyboard Setup Assistant for it. The helper records a layout type for its output keyboard
  in `/Library/Preferences/com.apple.keyboardtype.plist` before creating it.
- Device creation fails while Input Monitoring is denied, so the helper rescans after a grant.
- launchd kills a job's process group when the job exits; `AbandonProcessGroup` keeps the shared
  driver daemon alive across a helper crash, while the crashed client's virtual keyboard is torn
  down with its keys released.

## Not yet proven

- **Physical keyboards.** All input here came from a virtual source keyboard. The built-in
  keyboard and the Keychron Q6 HE have not produced reports through the helper
  (`ESC-PHYSICAL-KEYBOARD-EVIDENCE`).
- **Forwarding fidelity for real devices**, owned by `MS-CAPTURE-BEHAVIOR`: the built-in
  keyboard's `FnFunctionUsageMap`/`FnKeyboardUsageMap` translations (F-row media keys,
  fn+arrows), pointer collections on composite devices such as the Keychron Q6 HE (mouse keys),
  Caps Lock LED state, and non-ANSI layout types.
- Hung-helper recovery (watchdog), device removal, sleep/wake and session switching.
